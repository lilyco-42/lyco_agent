# 泛用性规划：学会未见 CLI，从 `--help` 推断「命令 / 结果 / 下一步」（2026-09-21）

> **用户需求（原文）**：
> > 「需求写的是『7 个固定工具』。**我根本不需要这个**，我强调 **brush shell** 实现。
> > **泛用性和对未知 CLI 未来 10 年发展依旧可用**。」
> >
> > 「持续达到这个目标。**学习未见 CLI**。推理 **`[cli] --help`**，
> > **从 help 推测结果和下一步**，你懂么。**重点规划泛用性**。」
>
> **本文档 = 该需求的落地路线图。** 依据 = v17~v19 全部实测（不引未验证的推断）。

---

## 一、一句话定义「做到」

> **给一个模型从没见过的 CLI，不问人、不改模型、不重训，
> 只需在机器上跑一次 `<cli> --help`，
> 就能把自然语言意图翻译成可执行命令，并知道「这条命令会输出什么、下一步该跑什么」。**

三条否定式约束（同样重要）：

| 不许 | 因为 |
|---|---|
| ❌ 不为每个新 CLI 训一次模型 | 训不了未来 10 年的 CLI（用户口径的核心） |
| ❌ 不写「7 个固定工具」的人工 schema | 封闭枚举，新工具出现即失效（用户已明确废弃） |
| ❌ 不靠「模型自己读 help 再提炼」 | v17/v17b 已证伪：提炼 = 信息抽取，0.6B 做不可靠 |

## 二、现状：机制已跑通，缺口是「覆盖深度」

### 2.1 已落地的链路（**这是「10 年可用」的载体**）

```
用户 NL
  └─ 域内五域 system prompt（hw/gh/ff/lb/brush）问一次
       ├─ 给出命令 → 走 T1 门
       └─ 说「无需调用」= 出域
            └─ guess_cli(nl)                      ← 从 NL 里猜 CLI 名（which() 校验）
                 └─ grab_help(cli)                ← 跑 `cli --help`（--help / -h / help 三级回退）
                      └─ parse_help(cli, raw)     ← ✅ Rust 确定性解析（零 GPU）
                           └─ readonly_only()     ← ✅ 只读过滤（安全）
                                └─ rank_by_frequency()  ← ✅ 高频排序
                                     └─ render_schema() ← ✅ 渲染成注入段
                                          └─ 二次询问 → 命令
                                               └─ T1 门 → 执行
```

**代码位置**：`lycore/src/help_parse.rs`（解析器）+ `lycore/src/router.rs:146 plan_with_help`（闭环）
+ `lycore/src/bin/lycore.rs:792 cmd_help_parse`（CLI 工具）。

**关键设计（已固化，不可回退）**：
- **提炼放在 Rust 侧，不放在模型侧**（v17 正解）。模型只做「从候选里挑 + 填参数」。
- **出域才触发自动接入**：`plan_with_help` 只在第一次回答判 Noop 时才二次询问（`router.rs:155`）
  → **对已训五域零回归**。
- **`brush` 是唯一工具出口**：模型输出 `brush <任意 CLI 命令>` 是产品合法通路。
  评测口径 = `strip_brush()` 剥前缀后判定（`acc_exec`）。

## 三、目标分解：90% 到底指什么

用户要求「**90 学会未来 CLI 陌生的 CLI**」。必须先把它拆成**可测的**三条，
否则 90% 是个无法判定、也无法交付的口号。

| 编号 | 目标 | 定义 | 当前 | 目标 | 测法 |
|---|---|---|---|---|---|
| **G1** | **命令正确** | 给出可执行命令，`strip_brush` 后与 gold 语义等价 | 近零样本 36.1% | **≥90%** | `acc_exec`（产品口径） |
| **G2** | **推断结果** | 能说出「这条命令会输出什么」（不是瞎猜） | **未实现** | ≥90% | 见 §4.3 |
| **G3** | **推断下一步** | 能给出「看完结果接着跑什么」（多步闭环） | **未实现** | ≥90% | 见 §4.4 |
| **G4** | 安全兜底 | 危险/越权拦截，宁拒不放 | `git pull` 漏洞刚修 | 误放行 = 0 | T1 门 reject 组 |

**⇒ 关键判断：90% 不是在 4 个 CLI 上达 90%，而是在开放世界（连续抽新 CLI）上达 90%。**
所以**评测集必须持续换新 CLI**，不能固定 6 个 —— 否则就是变相的「7 个固定工具」。

> ⚠️ **写进流程**：每次报「泛用性 90%」必须附「这批 CLI 有几个是训练里没出现过的」。
> 若 CLI 全都见过 → 这个 90% 不算泛用性证据。

### 4.1b ⚠️ P0.4 的前提被本次实测证伪：`--deepen` 救不了 git

原计划（引自 v19 §3.3）：「用 `--deepen` 对 top-N 子命令跑 `<cli> <sub> --help` 拿 usage 行，
验证能否自动补出 `--oneline`/`--stat`」。

**本次实测（本机，四处穷举）：**

| 取法 | 结果 |
|---|---|
| `git log --help` | ❌ `fatal: documentation file not found`（PortableGit 未装 html 文档） |
| `git help log` | ❌ 同上 |
| `man git-log` | ❌ `man: command not found` |
| `git log -h` | ⚠️ 720B，且 **`--oneline` 不在其中**（只列 `--quiet`/`--source`/`--decorate*` 等冷门 flag） |

**⇒ 结论：git 的「`--oneline` 在 help 里」这个前提不成立。**
`--deepen` 机制本身是对的（docker `logs` 需要容器名那类确实能补），
但它**对 git 无效**，因为 git 在这个环境里根本拿不到子命令的完整文档。

**⇒ 这同时解释了「裸 help 100.0% > hparse 87.5」的真机理（比 v19 的说法更精确）：**

```
裸 help  → 没给 --oneline，但也**没有干扰** → 模型靠自己的先验输出 `git log --oneline` → 100%
hparse   → 只给 8 条无参数骨架（status/log/show/branch/diff/grep/tag/fetch）
           → 把模型往「只输出 `git log`」上推 → 丢掉 --oneline → 87.5%
```

**即：不是「结构化注入丢了信息」，而是「结构化注入用一个更弱的形态
覆盖了模型本来正确的先验」。** 这与 B 档 kubectl（先验遮蔽）是同一机制的两个方向：

| 档 | 先验 | 注入 | 结果 |
|---|---|---|---|
| **B** kubectl | 有高频常见命令 | 想纠正它 | 先验**赢**（33.3，改注入无效） |
| **D** git | 有高频常见命令 | **没纠正，反而给了弱形态** | 先验被**削弱**（87.5 < 100.0） |

**⇒ P0.4 改设计（两条可选，均不需 GPU）：**

| 方案 | 做法 | 判据 |
|---|---|---|
| **A（推荐）** | **参数级线索不靠子命令 help**：对「薄 help」CLI，**直接保留原文 + 骨架双份**（= P0.1 已做），并**禁止骨架覆盖先验** —— 追加一句「若你已知道某个常用参数，可以加上」 | 需在 base06b 上跑 git 复测，看 87.5 是否回到 ≥100 |
| **B** | 装 git 的 html/man 文档（`git-doc`），再让 `--deepen` 真正拿到参数表 | 环境依赖重，不适合端侧；**仅作研究对照** |

**⚠️ 由此得出一条通用规则（写进流程）：**
> **注入的强度必须与 help 的信息量匹配。**
> help 信息量充足 → 骨架注入（更强、更省 token）；
> help 信息量不足但模型先验强 → **只追加原文、不做骨架替换**，否则是负优化。
>
> 判据（确定性）：`readonly_only().len() < 15` **且** 该 CLI 在模型先验里高频
> （高频 = zs-cli 这类零样本基线 > 50%）→ 走「原文优先」路径。

### P1 — 让「推断结果」成立（**G2，用户明确要求，当前完全空白**）

这是**本次需求与既往路线的最大差异点**：之前只做「NL → 命令」（一步），
用户要的是「NL → 命令 → **结果** → **下一步**」（闭环）。

**推断结果的机制（不训模型，全用确定性 + help 文本）**：

| 手段 | 做什么 | 为什么可行 |
|---|---|---|
| **① 输出模式标注** | 从 help 的 description 里抽输出形态，注入时带上：「`git log --oneline` → 每行一条提交」「`docker ps` → 表格：容器 ID / 镜像 / 状态」 | help 的描述文本**已含**这些信息（如 `Show commit logs`），只是当前解析器**只用了动词名，没用描述**（v19 §4.4 的同源认识） |
| **② 读-写-删动作分类** | 把每条动作标成 `查询/变更/破坏`，变更类**必须**提示「这会改状态」 | T1 门已有 `Risk` 三档，直接复用 |
| **③ 空结果提示** | 对查询类命令，预置「若输出为空 / 报 not found，说明 X」 | 可声明式写，不进模型 |

**⚠️ 必须验证的边界**：模型说出的「结果」是**真从 help 推的**，还是**背先验**？
判法同 v18f：**同一命令改 help 文本，输出的「结果描述」是否跟着变**。
不变 = 背先验 = 不算推断（这是 B 档 kubectl 的翻版，必须防）。

### P1 — 让「推断下一步」成立（**G3，用户体验的关键**）

| 手段 | 做什么 |
|---|---|
| **① 动词链** | 从 help 的动作集合里构造确定性后继图：`logs` → 若报错 → `describe`/`events`；`build` → `run`；`get` → `describe`。**规则可声明式写**，不训模型 |
| **② 失败分支** | 命令退出码非 0 → 用**同类动作**给候选（不猜，从同一 CLI 的 help 里取） |
| **③ 多步闭环节点** | 在 `Plan` 里加 `next_hint: Option<String>`，由 Rust 侧填，**不让模型自由发挥** |

**⚠️ 与已固化结论的一致性**：`lyco-skill` 链路裁决已定「**自由推理禁入**」
（When2Tool 79.5 → 31.2 的实证）。所以「下一步」**必须是查表结果，不是模型生成的一句话**。

### P1 — 评测集必须持续换新 CLI（**否则 90% 是假的**）

## 六、三条不能碰的红线（来自既往血训）

| 红线 | 出处 | 违反后果 |
|---|---|---|
| 🔴 **提示里绝不能出现孤立的名词列表** | v18d/v18e 两次失败同因 | 模型把列表里的词提升成命令（`kubectl svc`） |
| 🔴 **附加信息必须显式声明类别** | v18d | 被归到 schema 主类别「命令」里去 |
| 🔴 **推理是确定性的（greedy）** | v18f 三轮标准差 0.00 | 跨轮差异**全是 schema 内容效应**，不是噪声 → 不能拿「±10~16pp 噪声」当借口 |

**外加两条工程纪律**：
- 🔴 **聚合必须按显式 arm key 取值**（`d["v13"]`），禁用 `values()[0]` —— 曾算出反向结论。
- 🔴 **先测再断言** —— v19 的「git 分组标题被误判」假说被自己的实验证伪；
  照假说改代码会把正确逻辑改坏。

## 七、待用户决策的两点

1. **G1/G2/G3 的 90% 口径**：是「每个 CLI 都 ≥90%」，还是「开放世界平均 ≥90%」？
   本文档按**后者**规划（前者在一个 DSL 型 CLI（jq 类）上可能物理不可达，
   因为 `.name` 这类**用户数据结构信息根本不在 help 里**）。
2. **阶段 2/3 是否需要 GPU**：不需要。可在 CloudStudio 排不上队时先推进。
   但阶段 4 的 B 档治理（P0.3 换底座）**需要 GPU**。
