### 9.3 「少训练假设」结论

**成立，且强度排序与训练量单调反向：**
1. **训练量越少，跨域先验保留越好**：1ep(58.3) ≈ 4ep+lr5e6(58.3) > 2ep(56.7) > 4ep+LoRA(53.3) > 4ep全参(41.7)。
   四臂**没有一臂低于 v13**，全部落在 53–58 区间 —— 说明 v13 的 41.7% 主要败因是
   **4 epoch 全参 SFT 的过训练**，而非数据/配方。
2. **LoRA 的域内保真最优但跨域收益最低**（53.3，Δ+11.6 为四臂最小）。这与「LoRA 冻结底座
   ⇒ 先验完整保留」的预期**部分矛盾**：先验确实保住了（bash_held 14.0 持平、gh_A 仅 −1.1），
   但跨域迁移反而不如 1ep 全参 —— 说明 **跨域能力主要吃「底座权重被动过多少」，
   而非「先验是否被保留」**；LoRA 的 r=16 适配器本身也未充分学到域内任务表征。
3. **但四臂都远未追平 base 的 85.0%**。少训练只是**减少伤害**，不是**创造能力** ——
   与 §8 结论一致：**产品护城河在「注入协议 + 能力表 + T1 门」，不在权重**。
   若要真正逼近 85%，方向是 LoRA 调大 r / 更少 epoch 的组合，或直接零训练协议注入。

### 12.3 决策：**不 adopt、不替换，按「快判断层」有限 fork-extend**

**不能替换 v13 的三条硬理由**：
1. 🔴 **Jev 不能出命令**——我们产品核心输出是 `brush <cmd>`；Jev 只能说"这是 brush 域"，
   给不出 `find /home/radxa -size +100M`。**没有命令生成，就没有产品。**
2. 🔴 **违背「普惠全人类设备」不变量**（e677ab6/a79f860）——Jev 必须联网 + API key，
   而我们的不变量是「不许绑死任何一块板 / CPU 永远兜底 / 离线可用」。
3. 🔴 **数据主权**——用户查询要上传 TypeSafe 服务器。

**值得借鉴的三点**：
| # | 借鉴点 | 落地方式 |
|---|---|---|
| 1 | **三原语拆解法**（Choice/Score/Noul） | v17 schema 拆成「域 Choice + 动作 Choice + 槽位 Noul/Score」，**判定归模型、组装归 Rust 代码** |
| 2 | **置信度门禁甜点值** | conf ≥ 0.7 → 放行 73% / 精度 93.9%，这个**曲线形状**可作我们 θ 阈值参照 |
| 3 | **出域识别 100%** | 印证「出域是纯语义判断」，v13 的 reject=0% 是**训练数据没覆盖**而非模型不会 → **直接支撑 P2-c** |

### 12.4 🔴 本轮最大洞察（信条 4 的产物）

**Jev 碾压我们的不是模型大小，是「任务定义」。**

| | 任务定义 | 后果 |
|---|---|---|
| 我们 v13 | 「输出完整命令字符串」 | 生成式，自由度高 → 格式病 + 跨域崩 |
| Jev | 「从 6 个选项选 1 个」 | 判定式，**无生成衰减** |

→ **推论：把「域判定」从命令生成里剥离出来单独做，可能是跨域 41.7% 的真正解药。**
→ **这条不依赖 Jev**，可以在我们自己的模型上直接验证（见 §13）。

v13 的评测是「输出命令 → 执行 → 看 exit code」，Jev 只能「选选项」。

| **simple-jev** | **候选落地路径** | **不训分类头**，读 next-token logits → 改造成本最低，可直接套到我们已有检查点 |
| **lay-mlx / localjev** | 暂不 | 平台特定（Apple / Bun），与端侧 Rust 栈不符 |
| **semantic-router (两个)** | 备选 | 无 LLM 的纯嵌入方案，若「快判断层」不需要语义推理可考虑 |

**核心决策**：**不 adopt 任何云端方案（Jev 本身），clone NanoJev + kev 做本地判定式验证。**

### 13.5 下一步（合并 §12 与 §13 的结论）

| 选项 | 动作 | 成本 | 价值 |
|---|---|---|---|
| **J-A（推荐）** | **本机验证「判定式 vs 生成式」**：用 v13/v15 检查点，评测从"输出命令"改成"选域标签"（复用 `a10_zs_cli_eval.py` 测集，只改 prompt），看跨域是否暴涨 | **$0，本机可跑** | **直接验证 §12.4 洞察，不依赖任何外部服务** |

**若 J-A 成立**，P2 的所有困惑（hw_B 单调恶化、四臂无序、LoRA 最差）都可能统一解释为

### 14.4 🔴 失败模式归因（最有诊断价值的一条）

v13 的 **19 个域判定错误**归类：

| 失败模式 | 条数 | 说明 |
|---|---|---|
| **误拒（输出 NOOP）** | **9** | **全部集中在 yt-dlp** —— 出域误判，**不是命令错** |
| **编造不存在的 CLI 名** | **10** | gh / tail / redis-cli / youtube-dlp / ff / pnpm / nccp / yltest |
| 域选错（合法但不对） | **0** | ← **一条都没有！** |

**⇒ 🔴 0 条「合法 CLI 选错」是决定性的**：
v13 **不是「不会选」，是「不知道该域存在」**——要么误拒，要么即兴编一个像样的名字。
**这是「覆盖（coverage）问题」的教科书症状，与生成能力无关。**

### 14.5 假说裁定

**原假说**（§12.4）：
> 「Jev 碾压我们的不是模型大小，是任务定义（判定式 vs 生成式）」

| 判定 | 内容 |
|---|---|
| ❌ **证伪** | 「难在生成，判定式就能救」—— L1/L2 落差仅 5-17pp，**生成不是瓶颈**。v13 的域判定本身就差 |
| ✅ **部分成立** | Jev 在**训练未覆盖的域**上确实碾压（yt-dlp +83.3pp，CI 不跨零） |
| 🔄 **修正** | 真正的自变量是 **训练数据覆盖面（coverage）**，不是任务定义 |

**决定性反证**：v13 在 **kubectl / terraform 上反超 Jev**（100% vs 91.7% / 66.7%）。
→ **在训练覆盖到的域上，0.6B 是够用的，不需要 Jev。**
→ 「判定式 vs 生成式」不是主因；「覆盖 vs 未覆盖」才是。

### 14.6 与 P2 结论的合流

这个修正**恰好回到 P2 的结论**，三条证据链合流：

1. §9.3 **hw_B 随训练量单调恶化**（A0 −8.8 → A3 −31.6）——不是容量问题
2. §12.3 探针 3 **出域拒绝 10/10 = 100%**（v13 是 0%）——出域是纯语义判断，
   v13 的 0% 是**训练数据没覆盖**，不是模型不会
3. §14.4 **0 条「合法 CLI 选错」**——v13 不知道域存在，不是不会选

→ **P2 的全部困惑**（hw_B 单调恶化 / 四臂无序 / A3 LoRA 最差）统一解释为：
   **不是「容量不够」，不是「训练量不对」，不是「任务定义错配」，而是「覆盖（coverage）」。**

### 14.7 统计效力声明（引用必读）

- 第二层 n=60，McNemar p=0.0169 **显著**，方向可信；
- **但分 CLI 每格仅 12 条**，单格 95% CI 宽达 ±20-40pp →
  docker / kubectl 两格力「跨零」，**不能单独下结论**；
- yt-dlp(+83.3)/npm(+41.7)/terraform(−33.3) 三格 CI 不跨零，可信；
- 分层分析每层 12 条，**层间差异不可直接比较**（样本量不足）。
