## 0. 一句话目标

**让 4GB 内存的 ARM 板（A7A）和一台安卓手机，在离线状态下，把用户的大白话变成正确的 CLI 命令并安全执行；
而且新 CLI 不断出现时，零训练、零重训就能继续用。**

## 1. 用户与场景

| 项 | 内容 |
|---|---|
| 用户 | **不懂命令行的普通用户**（"小白机"），不是开发者 |
| 设备 | A7A（4GB / 8 核 ARM，无可用 NPU 跑 LLM）· 安卓手机（8–12GB，有 NPU） |
| 典型任务 | 看容器状态、清理文件、转视频、查持仓、装包…… |
| 隐含要求 | **十年可用**（不能靠"训过哪几个 CLI"活着） |
| 交互形态 | 选择题（模型给候选、用户挑）优先；不追求闲聊 |

## 2. 硬约束（不可谈判）

| 约束 | 值 | 来源 |
|---|---|---|
| 内存 | A7A 4GB / 手机 8–12GB ⇒ 模型 Q4 后 **≤1.2GB** 为佳 | 设备实测 |
| 离线 | **必须能离线跑**（联网仅作可选增强，不能是依赖） | 普惠不变量 |
| 许可 | Apache-2.0 / MIT（商用干净） | 产品化 |
| 安全 | 破坏性操作**误放行 = 0**；拒绝不能靠 SFT 权重 | 三次实测 |
| 语言 | 中文优先 | 目标用户 |
| 算力 | 训练/评测走 CloudStudio 或 Kaggle 免费额度；**板子只做端侧推理**（不做重负载） | 用户 2026-09-22 定 |
| 体积 | 端侧交付物 md5 存档、跨机必校验 | 2026-09-22 SD 卡事故 |

## 3. 设计前提（已被实验确立，**不要再重新论证**）

1. **Δ_SFT = −43.3pp**：跨域 exec 上 **未微调底座 85.0%** 高于任何训练臂（v13 41.7 / v16 38.3 / v14 8.3 / v15 3.3）。
2. ⇒ **护城河 = 注入协议 + 能力表 + T1 门，不在权重**。
3. **域内指标不携带泛化信息**（四臂域内打平、跨域差 8 倍）⇒ 排路线只看跨域 exec。
4. **底座是主效应**：换错底座 −33pp ≈ 配方效应的 7~10 倍（GDN 是归纳偏置错位，不是规模问题）。
5. **聊天域同样净损害**（两次独立 A/B：7/7/10 与 9/3/12 vs 原版 13/7/4 与 15/3/6）；
   SFT 唯一真实收益是**快 4×、无思考前缀、24/24 能在预算内作答**（原版 5/24 出不来）。
6. **runtime 优先**：8,199 次真实 Agent 运行中，**75.7% 的"模型失败"发生在成功调用工具之后**；
   只修 5 个 runtime bug、不动模型，6 个模型在 30 个单元改善 6~21 个（第三方论文）。
7. **单步变好 ≠ workflow 变好**：SFT 后单步全改善，自主多轮严格完成率 ≤10.4%（第三方论文）。
8. **端侧峰值 tok/s 会骗人**：手机第二轮掉一半、触发频率地板；Hailo-10H 只有 6.9 tok/s 但 20 轮零衰减。

## 4. 需求清单（含验收标准）

### P0（不做完不算产品）

| # | 需求 | 验收标准（可测） |
|---|---|---|
| P0-1 | **泛用路由**：NL → `brush <任意 CLI 命令>` | 在 **L1 外部陌生池（14 个 CLI）+ L3 冷门/异形** 上跨域 `acc_exec` ≥ **85%**（= 底座天花板）。**报分必须附「这批里有几个训练没见过」** |
| P0-2 | **零训练接入新 CLI**（`--help` 读手册） | 连续抽新 CLI（不训练）可用；判据 = **schema 是否真被采用**（而非分数高低）；help 改动用 `scripts/helpfixtures/` 逐字 diff，池内差异必须 = 0 |
| P0-3 | **执行层安全闸门** | 红队集上 **破坏性操作误放行 = 0**；解析顺序确定性：`registry.contains → schema.validate → arg type → capability.check → execute`（模型只给候选，不决定存在性） |
| P0-4 | **端侧可跑且可持续** | A7A：Q4 模型 `tg128 ≥ 20 t/s`（已达成 23.46）、**RSS ≤ 2GB**、**20 轮 sustained 衰减 ≤ 20%**、给出 `tokens/Joule` |

## 5. 明确不做（Out of Scope）

- ❌ 端侧跑 27B 级模型（权重放得下 ≠ 带宽够；A7A 更不可能）；
- ❌ 端侧 VLM（多模态塔白占内存，Qwen3.8-27B 即因此被否）；
- ❌ 把「安全拒绝」寄托在 SFT 数据上（实测两端都会放行删库命令）；
- ❌ 用「7 个固定工具各达 90%」当验收（封闭枚举，用户已明确否定）；
- ❌ 依据厂商 TOPS / 自述保留率排路线（等第三方 tokens/s、TTFT、RSS、持续功耗）。

## 6. 推荐路线（我的判断，明确表态）

### 6.1 停止一条线
**停止「用全参 SFT 提升 0.6B 能力」**。三个域、五次实验、两个运行时，结论一致为负；
v2（换掉 moss-003）只是在验证「数据选得对不对」，不是翻盘路线。

### 6.2 主推：Task Escalation，而不是 Model Escalation

```
用户请求
   │
   ▼
Tier-0  Needle 121M（路由/判定：选哪个 CLI、要不要动手）
   ├─ 明确 → 确定性 resolver（registry→schema→capability）→ T1 门 → 执行
   └─ 模糊/复杂
         ▼
      Tier-1  Qwen3-0.6B/1.7B Planner（注入协议 + --help 读手册）
         ├─ 解决 → 执行
         └─ 仍不行 → Tier-2 云端（**可选增强，不是依赖**）
```
理由：Tier-0 的 121M 在 RAM/延迟上比 0.6B 低一个数量级，且它的设计（**无匹配 tool 就输出空列表**）
正对着我们最烂的指标（**拒绝率 0%**）。

### 6.3 顺序上先做「零模型成本」的两件
1. **runtime 确定性 resolver**（论文证据：修 5 个 runtime bug 改善 6~21/30）；
2. **Failure Ledger**（不先能归因，就会把所有问题都误判成"模型太小"）。
这两件做完，才知道剩下的窟窿到底该用「更大模型」还是「更好的 runtime」去补。

### 6.4 训练只在有「不磨先验」的配方时才做
LoRA / 半 epoch / 先验域 replay / 只补格式与身份的小样本；**验收线 = 打平或超过未微调底座**，
达不到就不合并（宁可零训练，靠协议 + 门）。

## 8. 需要你拍板的三件事

1. **A7A 能否跑一次 20 轮 sustained 基准**（pp/tg/温度/频率/功耗 → tokens/Joule）？
   这与你「板子不做重负载」的约定冲突，我倾向跑（约 20 分钟、2 线程），但要你点头。
2. **是否投入 Needle 3 集成**？它是**自定义引擎（非 GGUF）**，接进 lycore 有工作量；
   但回报是 Tier-0 的 RAM/延迟降一个数量级。
3. **云端 Tier-2 要不要保留**？保留会打破「纯离线」，但只作为可选增强（默认关闭）。
