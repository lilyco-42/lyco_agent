## 0. 裁决摘要

**用户的判断成立，但需要精确化：** 「基础模型能力」确实是我们最大的瓶颈——但
在我们这个任务上，它不等于「参数量更新、更大的底座」，而是
**「底座要有精确的逐 token 检索/复制先验，并且不能让 SFT 把这个先验磨掉」**。

三条硬结论：

1. **底座的主效应约为数据配方的 2 倍**（跨域 acc_exec：24.3% → 6.5%，同配方只换底座）。
2. **我们换的新底座（Qwen3.5-0.8B，Gated DeltaNet）结构性不适合本任务**，不是调参能救的。
3. **【已闭环，且结论比预想严重】** 未微调底座（Qwen3-0.6B，零样本 + schema 注入）
   跨域 acc_exec 均值 **85.0%**，而 SFT 后的 v13 只有 **41.7%** →
   **Δ_SFT = −43.3pp**。**SFT 不是「挣来了 41.7%」，而是「从一个高得多的起点砍掉了一半以上」。**

�� **本报告最重要的一句话**：我们现在这 4000 条 SFT 数据的作用是**负的**——
它教出了域内格式（hw_A 98.8 / noop 94.4），代价是**磨掉了预训练自带的零样本 CLI 迁移先验**。
「提高基础模型能力」的正确动作因此不是换底座、也不是加数据，而是
**搞清楚怎么在保住域内的同时不磨掉先验**（少训练 / LoRA / 先验域 replay）。

由此产生两个具体止损：
- **原计划的「傅里叶 v2 = 1B + 重组」应重排**（§5）——加数据在这个背景下是加害。
- **v13 的 `reject = 0%`** 与「safe」不是同一件事的补充证据：base 臂 reject 同样 **0%**
  → 拒绝能力**从来不是** SFT 磨掉的，是**底座压根没有**（§4.5 表 D）。

## 3. 根因：为什么 0.8B GDN 会崩

Qwen3.5 用 Gated DeltaNet 替换了 75% 的 softmax 注意力层（3:1 hybrid）。
GDN 的核心是把历史压缩进**固定大小状态 S**：

> "Full attention can access prior tokens directly. Gated DeltaNet has to compress
> the past into a fixed-size memory state. That is efficient, but it is also a
> **bottleneck**."（Raschka, LLMs-from-scratch, Gated DeltaNet 章节）
> "Pure linear attention loses **precise token-to-token lookup**."

而**我们的任务恰恰是「精确逐 token 复制/对准」**：NL → 一字不差的 CLI 字符串
（flag 名、参数顺序、路径值都得准）。0.8B 层数少 → 那 25% 的 full-attention
「精确检索检查点」也少。**这不是规模问题，是归纳偏置错位。**

→ 这也是为什么 0.8B > 0.6B 却崩得稀碎：**字符串精确生成任务上，全注意力 > 混合线性注意力**。

## 4. 方法缺口（必须先补，否则一切结论悬空）

**我们从未测过「未微调底座」的跨域能力。** 所有跨域数字（24.3% / 6.5% …）都是 SFT 之后。
于是有一个无法回答、却决定路线的问题：

> **Δ_SFT = SFT 后的跨域 − 底座 zero/few-shot 的跨域，是正还是负？**

- 若为**负**：我们一直在用 SFT 磨掉预训练先验。
  → 「提高基础模型能力」的正确动作是**少训练**（LoRA 低秩 / 更少 epoch / 预训练语料 replay），
  而不是换底座或加数据；傅里叶式数据工程更是南辕北辙。
- 若为**正**：先验确实被 SFT 激活了 → 才轮到「挑一个先验更好的底座」。

这条实验**不需要训练**（只需推理一轮，成本≈1 小时 GPU），却能解锁全部其余结论。
在它出结果前投任何一次长训练，都可能是在错误的方向上加码。

- 臂 A（新增）：`Qwen/Qwen3-0.6B` **原始权重**，零样本，协议与 SFT 臂**逐字相同**
  （同一 401 行评测脚本、同 schema 注入块、同 greedy、同 `enable_thinking=False`、
  同 5 个 CLI × 4 个 arm × reject 集）。
- 臂 B（归档）：`router_v13_real_gh`（同底座 + 4000 条 v13 配方 SFT）。

### 4.5.1 这个发现改写了什么

| 原判断 | 修正后 |
| --- | --- |
| 「24.3% 是 SFT 挣来的」 | ❌ 是 SFT 从 85% 磨下来的 |
| 「继续加数据/换更大底座」 | ❌ 先解决「怎么不磨先验」，否则加什么都白搭 |
| 「傅里叶 v2 = 加数据是优化」 | ❌ 在当前背景下**是加害** |
| 「reject 0% 可能是 SFT 副作用」 | ❌ 底座就是 0%，**永远是 T1 门的责任** |
| 「域内 acc 是进步信号」 | ⚠️ 域内涨（hw_A 98.8）**恰好与跨域崩同时发生** → 域内是**过拟合读数** |

**一个必须正视的可能性**：base 85% 里有一部分是**schema 块在上下文里直接给出了命令清单**
（`docker ps` / `docker images` … 带示例）——即**答案在 prompt 里**，
模型只需做「NL → 匹配最像的那条」。这**恰恰是我们产品要的形态**（协议式注入），
所以 85% 是有效数字；但它也意味着：
**我们 4000 条 SFT 数据在做的事情，本来靠 prompt 就能拿到，且 prompt 版本还更好。**

## 6. 那么「拓宽视觉/NPU/YOLO」还做不做

**不停工，但降级为低优先。** 理由：

- **不抢同一份资源**：#1–#4 在远端 GPU 跑训练/推理，T0 兜底（pure-Rust `tract`）
  与 `lycore vision` 在本机 Rust 侧推进，可并行。
- **已完成调研、边际成本低**：选型已定案（ORT-EP + tract Tier-0 + Apache-2.0 检测器），
  剩下的只是实现，不存在方向风险。
- **但它治不了 MVP 的最大风险**：MVP 第 3 桶「出域泛化 exec」现在只有 **24.3%**
  （而我们刚刚知道 0.8B 路线只有 6.5%）。这是 v13 最脆弱的一环 → **优先级应回到底座**。

**建议的资源分配**：视觉/E2E 只做「不占用 GPU」的部分（T0 骨架 + 接口），
一旦 #1 的基线出结果，GPU 全压底座线。

## 8. 结论（对用户「是否继续/如何重排」的正面回答）

**继续，但重心和动作都要换。**

- **视觉/NPU 线**：不停工、不降级到"以后再说"，但**只做不占 GPU 的部分**（T0 tract 骨架 + 接口）。
  它是**普惠**故事的地基，且选型已定案，边际成本低。
- **命令路由器线（主线）**：**从"训更多"转为"训更少、确认怎么才不伤先验"**。
  依据是本次实测：**未训练底座在跨域上比我们任何训练产物都强一倍**。
  这不是"训练没价值"，而是**揭示我们此前把训练当成了唯一提升手段**——
  实际上（a）prompt 协议已经能拿到 85%，(b) 我们的 SFT 在往下拉。
- **一句话给决策**：
  > **先别加数据、先别换底座。把「训练强度」这一维单独扫一遍（LoRA/半 epoch/replay），
  > 目标是让第一个训练臂摸到 85%。摸不到，就承认零训练路线更好，把 SFT 线降为研究支线。**
- **两条已固化的产品级约束**（不受上面结论影响，独立成立）：
  1. `enable_thinking=False` 必须经 `chat_template_kwargs` 传（否则空输出）；
  2. 安全拒绝在模型侧为 0%，**执行层 T1 门是唯一防线**。
